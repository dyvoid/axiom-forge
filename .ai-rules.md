# Axiom Forge — AI Rules

This file establishes the ground truth for working within this repository. Read and strictly adhere to these rules before executing any code changes.

## 1. Documentation Integrity (Zero Tolerance)
You are **never** allowed to conclude a feature task or architecture change without updating the documentation.
- **`docs/`**: Always update the System Manual (`Architecture.md`, `Data_Model.md`, `Design_System.md`) to reflect the *current* state of the code. Never document what the code *should* do, only what it *does*.
- **`adr/`**: Use Architecture Decision Records for any new feature or architectural shift.

## 2. The Markdown Source of Truth
The `.md` files in a user's project folder *are* the database.
- Axiom Forge is a lens, not a lock-in.
- All markdown must remain 100% compatible with standard Markdown and **Obsidian**.
- Never introduce proprietary markdown syntax that breaks standard reading. Wikilinks (`[[Folder/Name]]`) are the standard.

## 3. Technology & Styling Constraints
- **Architecture**: npm workspaces monorepo (`shared`, `client`, `server`).
- **Styling**: Pure CSS Modules only. **DO NOT** use Tailwind, styled-components, or inline styles for layouts. Maintain the print-aesthetic (refer to `docs/Design_System.md`).
- **State**: The server holds state only in `projectStore` (in-memory). The client uses `TanStack Query` and `ProjectContext`. Do not introduce new state management libraries (no Redux, Zustand, etc.).

## 4. Single Source of Logic
- All markdown parsing and structured data validation lives in the `shared` package (`shared/parser.ts` and `shared/schema.ts`).
- Neither the client nor the server should implement bespoke parsing logic. If the format changes, change the shared parser.
